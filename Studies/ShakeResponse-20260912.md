# 빠른 흔들림 진단 — 2026-09-12

사용자 build 6 녹화는 약 2Hz, 팔을 수평으로 들고 약 90도 왕복시킨 동작이다. 실제 가속도·회전 축·진폭은 미측정이다. 아래 합성 입력은 이 동작의 측정 재생이 아니다.

## 실험 계약

현재 앱 소스는 유지하고 `.build-cache/shake-response-20260912/LiquidSimulation.swift` 동결 복사본만 계측했다. 원본/복사본 SHA는 inputs.json에 있다. 중력/선형 가속도의 공통 계수 5.8과 23.2를 비교한다. 범선 부력에도 같은 공통 계수를 써 힘의 균형을 유지했다. 점도·응집력·속도 제한·시간 간격·입자 수는 조절하지 않았다. prediction/constraint 속도 cap 발생 횟수만 추가했다.

- 120Hz, 1,200입자, 2초 정지 → 3초 2Hz 입력 → 3초 정지.
- translation: 중력 (0,-1,0), 선형 가속도 x=sin(4πt) g.
- roll: 선형 가속도 0, 화면 안의 중력 방향만 ±45도로 2Hz 회전. 현재 모델처럼 각속도/각가속도 관성은 없다.
- 같은 executable의 force-scale 인자만 다르게 실행. 각 실행의 trace.csv/summary.json 보존. Studies/ShakeResponse.swift는 offline 전용이며 앱 target에 포함하지 않는다.

## 1차 관찰

translation의 3–5초 COM x 2Hz 성분 진폭은 .01317 → .06088 scene unit이었다. 예측/밀도 보정 속도 cap 비율은 기준 0, 4배 .0243%/.0273%로 대부분 cap된 결과는 아니다. 3초 정지 후 energy는 .0912 → .3098로 늘었다. 공통 힘 계수 증가는 왕복을 키우지만 정지 상태에 부작용이 있어 앱에 채택하지 않는다. 이 숫자는 미감 점수도 실제 센서 응답 측정도 아니다.

이번 Mac CPU wall 측정은 step median 16.21/19.56ms, p95 77.79/172.50ms로 편차가 컸다. 이전 별도 M1 4step 프레임 중앙8.15ms 기록과도 달라 통제된 성능 비교로 쓰지 않는다. read-only 프로세스 확인에서 당시 Swift/Instruments 연산이 CPU를 점유하는 근거는 없었다. iPhone 시간 비율은 별도 opt-in 집계로 측정한다.

## 기기에서 확인한 시간 진행

build 7의 opt-in 20초 집계는 599개 accepted frame, acceptedHz 29.921, 물리시간/집계 대상 실시간 비율 .99779였다. 250ms 초과 제외 구간은 0개였다. CPU simulation 중앙값 17.97ms, GPU 실행 중앙값 29.51ms였다. 이 실행에서는 물리 시간이 지속해서 누락되는 현상은 관찰하지 못했다. acceptedHz는 표시 FPS가 아니고, 이 계측은 실제 센서 진폭·축·입력 지연을 측정하지 않는다.

## 중력 보존 후보 (후속)

동결 복사본에서 선형 가속도 항만 5.8 → 23.2로 변경했다. 중력과 범선 부력은 5.8을 유지했다. 따라서 입력 가속도가 0인 최초 정지 2초의 center/energy/topY는 기준과 같았다.

1g 2Hz translation의 center x 진폭은 .01317 → .13619 scene unit, 3초 흔든 뒤 topY는 -.544 → .956이었다. 예측/보정 속도 cap 비율은 .0115%/.0802%로 대부분 잘린 출력은 아니다. 3초 정지 후 energy .14546, center y -1.41366으로 복귀했다(기준 .09123, -1.40757). 최초 후보의 정지 잔떨림 증가보다 작지만, 실제 handfeel이나 충분한 정착 시간 통과를 확정하지 않는다.

같은 초기 상태의 6초 native 렌더 A/B를 완료했다. 후보에서 큰 기둥과 분리된 방울이 생겼지만 실물 같은 질감이나 적절한 세기까지 통과한 것은 아니다. 기존 물리 검사 15개 중 마지막 수면 기포 추적 검사가 후보에서 실패했다. 앞선 14개 검사 통과만으로 이 후보를 앱에 채택하지 않는다.

## 1·2·3Hz 비교

같은 이동 폭을 단순화한 합성 선형 입력으로 주파수 1·2·3Hz에 각각 1·4·9g를 사용했다. 실제 팔 동작의 가속도 측정값이 아니다. 앱과 같은 3g 입력 제한과 동일한 고정 시간 간격을 적용했다. 3–5초의 center x에서 입력 주파수 성분의 진폭을 구했다.

| 주파수 | 입력 진폭 | 3g 초과 입력 비율 | 기준 진폭 | 선형 관성 4배 후보 진폭 |
| --- | --- | --- | --- | --- |
| 1Hz | 1g | 0% | .05834 | .47768 |
| 2Hz | 4g | 43.3% | .11306 | .37191 |
| 3Hz | 9g | 75.0% | .05692 | .23874 |

이 실험에서 기준은 2Hz보다 3Hz의 왕복 진폭이 작았다. 후보도 1Hz보다 2·3Hz의 진폭이 작았으며, 예측 속도 제한 비율이 전체 8초 기준 3.33%·14.07%·7.59%로 증가했다. 선형 관성 항을 4배로 키우는 것만으로는 원하는 주파수 응답을 얻지 못했다. 입력 제한이 빠른 응답을 줄이는지 다음에는 힘 계수를 유지하고 제한만 바꾼 대조 실험으로 분리해야 한다. 로그 형태의 입력 압축도 아직 채택하지 않았다.

## 저장소에서 재현

`Studies/Fixtures/ShakeSimulation.swift`는 중력을 보존하고 선형 관성 계수만 바꾸는 후속 실험의 동결 솔버다. 앱 target에는 포함되지 않는다. 현재 앱의 솔버는 `SmallWave/Core/LiquidSimulation.swift`다. 최초 공통 중력 계수 실험과 이 fixture를 혼동하지 않는다.

```sh

sh scripts/study-shake-response.sh 5.8 2 4
sh scripts/study-shake-response.sh 5.8 3 9
sh scripts/study-shake-response.sh 23.2 2 4
```

각 실행은 `.build-cache/shake-response/`의 새 폴더에 결과를 저장한다. 영상은 합성 2Hz·1g 입력이며 현재 앱 렌더러를 사용한다. 최초 A/B 시점 이후 범선 리소스가 바뀌었으므로 옛 영상과 픽셀 일치를 요구하지 않는다. 추가된 두 실행 경로의 Swift 타입 검사와 셸 구문 검사를 통과했다. 위 수치의 동결 실행은 별도로 완료했으며, 새 wrapper로 모든 경우를 다시 실행한 것은 아니다. 현재 앱에는 이 연구의 힘 계수 변경을 적용하지 않았다.

## 입력 제한만 완화한 후보

힘 계수 5.8, 중력, 점도, 입자 속도 제한을 유지하고 센서 가속도 상한만 3g → 12g로 올렸다. 앞선 관성 4배 후보와 다른 변경이다. 합성 이동 폭 조건의 결과는 다음과 같다.

| 주파수 / 입력 | 3g 제한 COM 진폭 | 12g 제한 COM 진폭 |
| --- | --- | --- |
| 1Hz / 1g | .05834 | .05834 |
| 2Hz / 4g | .11306 | .13619 |
| 3Hz / 9g | .05692 | .15765 |

120Hz 물리 경계 검사 15개를 통과했다. 100Hz 센서를 30Hz 렌더 프레임으로 소비하는 3Hz·9g 검사에서도 양/음 피크 약 ±8.982g가 유지됐다. 이는 실제 팔 동작을 측정한 결과가 아니다. 실제 입력이 3g 이하라면 상한 변경만으로 해당 동작을 개선했다고 설명할 수 없다.

개발자 실행의 기존 20초 로컬 타이밍 보고서에 센서 수신 개수, 원래 가속도 최대값, 3g 초과 개수, 각속도 최대값, 센서→콜백 지연 최대값, 동작 줄이기 설정을 추가했다. 숫자 집계만 저장하며 일반 아이콘 실행에서는 기록하지 않는다. `motionSession`은 센서 시작/초기화 이후 집계로, 정확히 20초 구간에 한정된 값이나 센서→화면 지연이 아니다. 실제 기기에서 새 입력 상한의 효과와 시간 진행을 다시 확인해야 한다.

네 번째 인자로 입력 상한을 재현할 수 있다: `sh scripts/study-shake-response.sh 5.8 3 9 12`.

연구 도구의 입력 기본주파수 진폭 집계는 전체 사인파를 작게 만드는 방식에서 실제 순간 가속도를 상한으로 자르는 방식으로 정정했다. 3Hz·9g·상한 3g 재실행에서 입력 기본주파수 진폭은 3.74853g, COM 진폭은 .05692479였다. COM과 물리 입력 계산은 이 집계 수정의 영향을 받지 않는다.

## build 10 실제 손 동작 측정과 설정 수정 — 2026-09-13

사용자가 준비됐다고 응답한 뒤 앱을 재실행하고 5초 느린 기울임 → 10초 빠른 흔들림 → 5초 정지를 요청했다. 사용자는 완료했다고 응답했다. 개별 동작의 정확한 시점·축·주파수는 영상으로 검증하지 않았다.

새 capture ID와 `appBuild=10`을 확인한 19.9678초 보고서는 accepted frame 599개, acceptedHz 29.9483, 물리시간/집계 대상 실시간 .99828, 250ms 초과 제외 구간 0개였다. GPU 실행 중앙값은 9.38ms, p95 30.73ms였다. 이전 build 7과 입력/자세가 같지 않아 성능 향상률로 비교하지 않는다. 정지 필터가 켜진 구간을 따로 집계하지 않았으므로 필터의 기기 비용을 단독으로 입증하지도 않는다.

센서 세션 2,022표본에서 raw 가속도 최대 3.582g, 3g 초과 8표본, 각속도 최대 10.149rad/s, 센서→콜백 지연 최대 6.316ms였다. **effective reducedMotion=1**이어서 물리로 넘기는 가속도가 0.2배였다. 기존 코드는 앱 토글과 시스템 접근성 설정을 OR로 합쳐 사용했으므로 어느 설정에서 비롯됐는지는 이 집계로 구분할 수 없다. 12g 상한 변경만으로 이번 불만을 해결했다고 볼 수 없다.

build 11은 앱 안에 `아이폰 설정 따르기 / 손 움직임 그대로 / 잔잔하게` 선택을 추가했다. 새 선택이 없으면 기존 앱의 잔잔함 선택을 보존하고, 그 외에는 시스템 설정을 따른다. 명시적으로 `손 움직임 그대로`를 선택하면 이 앱의 입력 약화만 해제한다. 전역 접근성 설정은 쓰지 않는다. 서명 빌드·앱/위젯 버전 확인·아이폰 설치/실행은 통과했으며 full 반응의 실제 손맛은 사용자 확인 대상이다.

첫 무인 측정 시도에서 읽힌 파일은 build 7의 예전 capture였으므로 새 검증에서 제외했다. 위 수치는 재실행 후 새 capture ID가 일치한 결과만 사용했다.

## build 14: 강한 흔들림의 입력 3배 — 2026-09-13

사용자는 `손 움직임 그대로`를 선택한 뒤 반응이 나아졌지만, 강하게 흔들 때 최소 3배쯤 더 격렬했으면 좋겠다고 요청했다. 이에 중력과 솔버 힘 계수는 유지하고 선형 가속도에만 세기별 이득을 적용했다.

- 가속도 크기 .15g 이하는 1배, .15–.65g는 smoothstep으로 1→3배, .65g 이상은 3배다. 이후 기존 12g 입력 상한을 적용한다.
- history에서 시간 순서대로 꺼낸 물리 표본 각각에 적용하며, 방향·시간·중력을 바꾸지 않는다. 120Hz 간격·속도 상한 5·입자 수·부력도 유지한다.
- `잔잔하게`와 시스템 `동작 줄이기`를 따르는 경로는 기존 0.2배를 유지한다. 저장된 선택 ID는 그대로이며, 입력 증폭을 반영해 옵션 이름을 `생생하게`로 바꿨다.

`sh scripts/test-shake-strength.sh`는 약한 입력, 이득 경계의 연속성, 방향, 비유한 값, 모드별 분기와 기존 상한을 검사한다. `sh scripts/study-shake-strength.sh .build-cache/shake-strength-new-run`은 현재 앱 솔버로 비교하며 기존 결과 폴더를 덮지 않는다. 단위 검사와 6개 합성 실행을 완료했다.

합성 조건은 1.5초 정착 후 3초 가속도 사인파다. 같은 이동 폭을 단순화해 1/2/3Hz에 .30/1.20/2.70g를 사용했다. 실제 팔의 회전이나 센서 로그 재생은 아니다. COM 기본파는 drive 마지막 정확히 2초(240 tick), 최고 수면·속도는 drive 3초만 집계한다.

| 입력 주파수 | 실제 적용 피크: 기존 → 변경 | COM 기본파: 기존 → 변경 | COM 비율 |
| --- | --- | --- | --- |
| 1Hz | .30 → .4296g | .016897 → .021139 | 1.251배 |
| 2Hz | 1.20 → 3.60g | .017783 → .119395 | 6.714배 |
| 3Hz | 2.70 → 8.10g | .043402 → .141945 | 3.270배 |

전 실행에서 1,200입자와 유한 값이 유지됐다. 3Hz 후보는 기존 속도 상한 5에 도달했다. 이 지표는 화면 이동 폭이나 모든 실제 동작이 최소 3배가 된다는 보장이 아니다. 빠른 동작의 입력 약화를 해제한 build 11의 효과와 이번 증폭을 혼동하지 않는다.

비교 자료는 로컬 `.build-cache/shake-strength-final-20260913/`에 보관한다. 두 3Hz 스냅샷은 같은 시뮬레이션 시간 4.500017초이며 마지막 실제 입력 표본 시각은 4.491667초다. 그때 raw x 가속도는 −.422378g, 변경 후 가속도는 −.901316g다. 마지막 순간을 가속도 0으로 표기한 이전 초안은 교정했다. 비정수 주기 2.5초를 사용한 이전 COM 수치도 위 표로 대체했다.

build 14의 서명 없는 iPhone 앱·위젯 컴파일을 완료했고 두 번들 버전 `0.1 (14)`와 고정 입력 32개가 현재 소스와 일치함을 확인했다. 초기 샌드박스 실행은 기존 Metal 도구에 접근하지 못했으나, 같은 고정 소스를 호스트 Xcode로 빌드해 통과했다. 추가 도구 설치는 없었다.

현재 설치된 폰은 build 13이다. build 14의 서명·설치·실제 손맛은 사용자 복귀 후 확인 대상이다. 수면 요철·물기둥·물성 미감이 해결됐다는 주장은 하지 않는다.
